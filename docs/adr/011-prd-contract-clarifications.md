# ADR-011：PRD 与实施契约待澄清事项

- 状态：提议，未批准；不修改现有 SAD、OpenAPI 或 DDL。
- 日期：2026-10-24
- 本次仅接收 PRD、编写计划；有冲突的实现必须等待决策。

## 1. 返回上一步与修改答案（P1 前决策）

PRD §4.7 要求返回上一步并修改答案。SAD §7.2 规定 completed/expired 探索不能继续提交；DDL 每探索每步骤唯一；OpenAPI 只有提交答案，没有明确替换答案及后续分支失效的语义。

备选 A：返回改答时创建新探索并复用同一 question_version，通过服务端逐步校验重放仍有效的前缀答案。旧探索、意图和已发起推荐保持不变；页面解释新结果以修改后的选择为准。可保留现有 API 结构，但须明确资源增长、限流和幂等处理。

备选 B：扩展原探索改答契约，事务内使下游答案失效，并定义完成状态、阅读意图与已创建推荐的处理。需批准并同步 SAD、OpenAPI、DTO、迁移（如需要）和测试。

建议 A，以保留不可变已完成结果；这只是提议，不能据此宣布 PRD 已满足。验收覆盖分支切换、跳过偏好、完成后改答、并发提交和旧书单不变。

## 2. 探索表唯一 Owner（P0 前确认解释）

SAD §3 将探索流程交给 exploration，§6 与 DDL 将探索表放在 content schema。schema 位置不必等于代码 Owner，故这里是归属歧义，不直接判定 DDL 冲突。

建议明确：`content.explorations` 和 `content.exploration_answers` 的唯一代码 Owner 为 exploration；题目及版本归 content，通过端口读取。保留表名与 schema，不迁表。

## 3. SSE 错误事件命名（P3 前统一）

SAD §5.2 写 `event:error`，§7.1 与 OpenAPI x-contract-rules 写 `message_error`。建议以明确的外部契约 `message_error` 为准，批准后修正文档表述，不增加第二套客户端事件。

## 4. 范围解释及尚需落地的产品决定

- PRD 功能优先级 P1 不等于交付阶段 P1；收藏、保存思考等不在本次 P0—P5 基线内。
- 学习基础、深度和“可能获得什么”需明确映射到现有意图字段及结果文案；若确实需要新增结构字段，先提契约变更，不静默扩展响应。
- 数据保留时间、删除流程与成人访问措施须在相关实现前确定；不能把“可配置”当作已作出产品决定。
- 性能值保留 SAD 的初始目标性质，最终验收必须注明测量条件与经确认的门槛。

## 影响与回滚

本 ADR 为提议，不执行 API/数据库变更。批准后在对应阶段 PR 中记录决定、测试与兼容性影响；若撤回本提议，删除或标记为撤回即可，无数据库回滚。
